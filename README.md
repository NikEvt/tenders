# Закупки 44-ФЗ — анализ, ИИ-фильтрация и рекомендации

Система собирает извещения из ЕИС (`zakupki.gov.ru`), скачивает и распознаёт
приложенную документацию, отвечает на запросы обычным языком, каждое утро готовит
сводку и рекомендует закупки на основе просмотров, оценок и выигранных тендеров.

## Что умеет

| Сценарий | Как работает |
|---|---|
| Гибкая фильтрация | Структурные условия по SQL + полнотекстовый поиск по карточке **и по тексту документов** |
| ИИ-фильтрация по содержанию | Дешёвый отбор кандидатов (лексика ⊕ вектор, RRF) → LLM-судья читает релевантные фрагменты ТЗ и выдаёт вердикт со ссылкой на источник |
| Фильтр из свободного текста | «поставка газа в баллонах, бюджет до 1млн руб» → структурный фильтр + семантический запрос + критерий для модели |
| Сводка дня | Map-reduce: резюме по категориям → общая сводка (крупнейшие закупки, новые заказчики, сдвинутые сроки) |
| Рекомендации | Взвешенный профиль интересов + ANN-поиск + объяснимое ранжирование, 15% выдачи — на исследование |

## Архитектура

Шесть сервисов, между ними — RabbitMQ. Внутри каждого сервиса три слоя, зависимости
направлены строго внутрь:

```
presentation  → HTTP-роутеры и AMQP-консьюмеры
application   → use-cases, порты (ABC), промпты
domain        → доменные модели и правила, без единой внешней зависимости
infrastructure → адаптеры портов: БД, MinIO, ЕИС, LLM, экстракторы текста
```

Правило проверяется автоматически: `lint-imports` запрещает импорты
`application → infrastructure` и кросс-сервисные импорты.

| Сервис | Роль | Порт |
|---|---|---|
| `api` | REST/OpenAPI, каталог, поиск, шлюз к остальным | 8000 |
| `crawler` | SOAP ЕИС → нормализация → `tenders` | — |
| `docs-worker` | Вложения → MinIO → текст/OCR → чанки | — |
| `embedding-service` | `deepvk/USER-bge-m3`, 1024-мерные векторы | 8020 |
| `llm-service` | qwen3.6-35B-A3B: фильтры, судья, сводка | 8010 |
| `recsys-service` | Профиль интересов, рекомендации | 8030 |
| `dashboard` | Временный UI на Streamlit поверх API | 8501 |

Поток событий:

```
tender.ingested ──▶ docs-worker ──▶ document.extracted ──▶ embedding-service
       │                  │
       │                  └──▶ tender.enriched ──▶ llm-service, recsys-service
       └──▶ embedding.requested ──▶ embedding-service

filter.evaluate.requested ──▶ llm-service      feedback.recorded ──▶ recsys-service
digest.requested          ──▶ llm-service
```

Надёжность: события публикуются через **transactional outbox** (запись в ту же
транзакцию, что и данные), потребители дедуплицируют по `message_id`, сбои уходят
в лестницу retry-очередей (5с → 30с → 2м → 10м → 1ч) и затем в dead-letter.

## Быстрый старт

```bash
cp .env.example .env          # заполните EIS_TOKEN, пароли, LLM_BASE_URL
docker compose up -d --build
```

Порядок старта задан в compose: сначала инфраструктура, затем миграции
(`alembic upgrade head`), затем сервисы.

- API и OpenAPI: http://localhost:8000/docs
- Дашборд: http://localhost:8501
- RabbitMQ: http://localhost:15672
- MinIO: http://localhost:9001

Разовая выгрузка за конкретный день:

```bash
docker compose run --rm crawler python -m services.crawler --date 2026-08-06 --once
```

### Подключение LLM

Годится любой OpenAI-совместимый эндпоинт. Из контейнера хост-машина доступна как
`host.docker.internal`, а не `localhost` — самая частая причина «модель недоступна».

**Yandex Cloud** требует трёх особых настроек, каждая иначе ломает работу молча:

```bash
LLM_BASE_URL=https://ai.api.cloud.yandex.net/v1
LLM_MODEL=gpt://<folder-id>/qwen3.6-35b-a3b/latest   # полный URI, иначе 400
LLM_AUTH_SCHEME=Api-Key                              # вместо Bearer
LLM_REASONING_EFFORT=none                            # см. ниже
```

Folder ID не нужно искать в консоли: укажите заведомо неверный и прочитайте ответ —
сервис пишет `does not match with service account folder ID '<ваш-id>'`.

`qwen3.6-35b-a3b` — reasoning-модель: на односложный ответ она тратит ~700 токенов
размышлений против 2 с `reasoning_effort=none`. Поэтому рассуждения выключены
везде, кроме LLM-судьи по документам (`LLM_JUDGE_REASONING_EFFORT=low`), где они
влияют на качество вердикта.

Структурный вывод (`response_format: json_schema`) Yandex Cloud не принимает.
Клиент это обнаруживает по первому отказу, переключается на `json_object` со
схемой в промпте и больше строгий режим не пробует.

Проверка, что связка работает:

```bash
curl -sX POST localhost:8000/filters/compile -H 'Content-Type: application/json' \
  -d '{"query":"поставка ламп с гарантией не менее 3 лет"}'
```

Признак успеха — **непустой `llm_criteria`**. Если он пуст, а `keywords` выглядят
как разбитый на слова запрос, значит модель недоступна и сработал деградированный
режим. Пустой `llm_criteria` на простом запросе («поставка газа») — норма: модель
считает, что структурных полей достаточно, и дорогой судья не запускается.

### Эмбеддинги на Apple Silicon

Контейнер `embedding-service` на Mac считает **на CPU**: Docker Desktop работает
в Linux-VM, куда Metal не пробрасывается, поэтому MPS внутри контейнера
недоступен принципиально. Чтобы задействовать GPU, запустите сервис нативно:

```bash
uv pip install --python .venv -e ".[embedding]"        # обычный torch, с MPS

DB_HOST=localhost RABBITMQ_HOST=localhost \
.venv/bin/uvicorn services.embedding_service.presentation.app:app --port 8020
```

Проверить выбранное устройство: `curl localhost:8020/health/ready` — в ответе
поле `device` (`mps`, `cuda` или `cpu`; выбирается автоматически, принудительно
задаётся через `EMBEDDING_DEVICE`).

Остальной стек тогда поднимается без этого контейнера, а сервисы направляются
на хост:

```bash
EMBEDDING_SERVICE_URL=http://host.docker.internal:8020 \
docker compose up -d --scale embedding-service=0
```

В Linux-развёртывании ничего этого не нужно: контейнер собирается с CPU-сборкой
torch (для GPU передайте `--build-arg TORCH_INDEX_URL=https://pypi.org/simple`).

## Поставка клиенту

Офлайн-сборка под Windows: один архив с образами, compose и `.bat`-скриптами,
устанавливается на Docker Desktop без доступа к registry.

```bash
scripts/build_client_bundle.sh 2026.08.17      # → dist/zakupki-2026.08.17-windows.zip
```

Скрипт собирает образы под `linux/amd64`, докладывает к ним образы
инфраструктуры, **проверяет, что ни один секрет не попал в слои или ENV**, и
пакует всё вместе с `deploy/client/`. В поставку не входят ни embedding-service
(torch и модель на 2 ГБ; поиск по документам у клиента остаётся лексическим),
ни какие-либо данные — тома создаются пустыми.

Токены клиент вводит свои: `.env` собирается у него из шаблона при первом
запуске, пароли внутренних служб генерируются там же. Инструкция, которая едет
клиенту, — [`deploy/client/INSTRUKCIYA.txt`](deploy/client/INSTRUKCIYA.txt)
(простой текст и латиница в имени: `.md` в Windows нечем открыть, а кириллица
в zip от Info-ZIP приезжает в проводник кракозябрами).

Вся логика запуска живёт в `.ps1`, а `.bat` — пустые пусковые файлы на ASCII.
Причина в `deploy/client/_common.ps1`; сборщик проверяет это правило и падает,
если в батник просочился не-ASCII символ.

Собирать лучше на amd64: на Apple Silicon стадия `docs` идёт через эмуляцию
и занимает десятки минут.

## Разработка

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv -e ".[crawler,docs,llm,recsys,api,dev]"

docker compose up -d postgres rabbitmq minio   # нужны для интеграционных тестов
.venv/bin/alembic upgrade head

.venv/bin/python -m pytest tests -q   # 135 тестов
.venv/bin/ruff check .
.venv/bin/lint-imports                # контроль слоёв
```

Интеграционные тесты идут против настоящих Postgres и RabbitMQ: генерируемые
столбцы, `ON CONFLICT ... RETURNING`, pgvector и лестница ретраев на моках не
воспроизводятся. Если сервисы не подняты, эти тесты пропускаются.

## Структура

```
libs/shared/        контракты событий, messaging, схема БД, конфиг, логирование
services/api/       каталог, поиск, шлюз
services/crawler/   выгрузка из ЕИС
services/docs_worker/     документы: скачивание, извлечение текста, OCR, чанкинг
services/embedding_service/
services/llm_service/
services/recsys_service/
migrations/         Alembic, единая история
dashboard/          Streamlit-клиент (HTTP, без прямого доступа к БД)
legacy/             код до рефакторинга, в сборке не участвует
```

## Безопасность

Токен ЕИС и пароли берутся только из `.env`, который в git не попадает. Прежний
токен лежал в открытом виде в `docker-compose.yml` и `test.py` (теперь
`legacy/test.py`) — **считайте его скомпрометированным и перевыпустите** в личном
кабинете ЕИС.

## Сертификат для доступа к ЕИС

`docker/certs/russian_trusted_root_ca.pem` — корневой сертификат Минцифры,
которым подписана цепочка `zakupki.gov.ru`. В стандартном бандле его нет, без
него TLS-рукопожатие не проходит.

Сертификат лежит в репозитории, а не качается при сборке: реестры регулярно
недоступны, и скачивание «на удачу» уже приводило к образу, который молча не мог
подключиться к ЕИС. Сборка проверяет, что сертификат попал в доверенный бандл,
и падает, если нет.

Срок действия — до 27.02.2032. Обновить можно отсюда:
`https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`.

## Диагностика выгрузки

ЕИС сообщает об отказах внутри HTTP 200, в `dataInfo/errorInfo`. Краулер такие
ответы разбирает и помечает запуск как `failed` — раньше заблокированный токен
выглядел бы как «за этот день закупок нет».

```sql
SELECT target_date, status, fetched, saved, error_message
FROM crawler_runs ORDER BY id DESC LIMIT 10;
```

Частые коды: `34` — организация заблокирована в личном кабинете ЕИС (нужен
действующий токен). Пустая выгрузка при `status='success'` — это не ошибка,
за конкретный день по региону могло не быть публикаций; проверяйте
`--days-back 3`.

## Известные ограничения

- Однопользовательский режим: аутентификации нет, профиль и оценки глобальные.
  Схема уже готова к переходу — у профиля есть идентификатор.
- 223-ФЗ не поддержан: нужен ещё один адаптер `TenderSourcePort`.
- `purchaseStatus` в извещениях ЕИС не приходит, поэтому статус вычисляется из дат.
- Ранжирование рекомендаций линейное и объяснимое. Обученный ranker подключается
  за тем же портом `RankerPort`, когда наберётся порядка 500 оценок.
