# Выгрузка по всей России и ручное обновление

План снимает три ограничения сбора: выгрузка идёт по одному региону, догнать
свежие извещения внутри дня нельзя, а заказать выгрузку из интерфейса нельзя
вовсе.

**Состояние на входе:** `EIS_REGIONS=77` — только Москва. В корпусе 1208
закупок за 6–13 августа 2026. Дневное расписание тянет вчерашний день
последовательно, в одной транзакции на все регионы. Заявка на произвольный
период (`CrawlRequested`) реализована и потребляется, но **не публикуется
никем** — путь мёртв с той стороны, с которой им пользуются.

---

## 1. Как данные подтягиваются сегодня

### 1.1 Расписание

```
контейнер стартует
   └─ _crawl_days(вчера)                        ← один проход сразу
        └─ transaction(session)                 ← ОДНА транзакция на все регионы
             └─ CrawlAllUseCase.execute(день)
                  for регион in EIS_REGIONS:     ← последовательно
                    for тип in EIS_DOCUMENT_TYPES:
                      CrawlTendersUseCase.execute(регион × тип × день)
   └─ _schedule_loop: sleep(60 мин) → повторить
```

Точки в коде: [cli.py:148](../../services/crawler/presentation/cli.py#L148)
(`base = date.today() - timedelta(days=1)`),
[cli.py:166](../../services/crawler/presentation/cli.py#L166) (интервал),
[crawl_tenders.py:107](../../services/crawler/application/use_cases/crawl_tenders.py#L107)
(двойной цикл), [docker-compose.yml:221](../../docker-compose.yml#L221)
(`EIS_CRAWL_INTERVAL_MINUTES=60`).

**Гранулярность ЕИС — сутки.** `get_by_region(region, document_type, target_date)`
([soap_client.py:188](../../services/crawler/infrastructure/eis/soap_client.py#L188))
запрашивает суточный архив и скачивает его целиком. Запроса «что появилось
после 14:32» в API нет и быть не может. Отсюда следует всё остальное в этом
плане: «обновить» может означать только «перекачать суточный архив и дать
дедупликации отработать».

Дедупликация уже есть: `upsert_many` бьёт по `reg_num`, возвращает `is_new`
([tender_repository.py:33](../../services/crawler/infrastructure/db/tender_repository.py#L33)),
а `docs-worker` не перекачивает уже разобранные вложения — `processed`
расходует бюджет, но решения не переигрывает
([admission.py:182](../../services/docs_worker/domain/admission.py#L182)).
Значит, повторная выгрузка дня стоит трафика на архив, но не на документы.

### 1.2 Два сценария вместо одного

| | `CrawlAllUseCase` | `CrawlPeriodUseCase` |
|---|---|---|
| Кто зовёт | дневное расписание | потребитель `crawl.requested` |
| Параллельность | нет | `crawl_workers` из уровня нагрузки (1/3/6) |
| Транзакция | одна на все регионы | своя на каждую выгрузку |
| Пропуск выгруженного | нет | да, по журналу запусков |
| Кто публикует заявку | — | **никто** |

Оба решают одну задачу — «выгрузить набор регион × тип × день», — и это
нарушение GRASP: у одной ответственности два владельца, причём худший из них
на горячем пути. Для 85 регионов последовательный обход в одной транзакции
неприемлем: транзакция висит на всё время обхода, а события `TenderIngested`
копятся в outbox до коммита.

### 1.3 Скрытая дыра в покрытии

`completed()` считает день выгруженным по `status='success'`
([run_log.py:42](../../services/crawler/infrastructure/db/run_log.py#L42)) — без
оглядки на то, **закончился ли день к моменту выгрузки**. Заказ периода,
включающего сегодня, успешно тянет частичный архив, помечает день готовым, и
остаток суток не будет выгружен уже никогда. Сегодня это не стреляет только
потому, что расписание берёт вчера, а заявки никто не шлёт. Кнопка обновления
превращает дыру в основной сценарий, поэтому чинится в том же этапе.

## 2. Что делаем

Три изменения, каждое опирается на уже существующий механизм.

1. **Сведение сценариев.** `CrawlAllUseCase` удаляется, дневное расписание
   переходит на `CrawlPeriodUseCase`. Один владелец ответственности,
   параллельность и посуточные транзакции достаются бесплатно.
2. **Правило завершённости дня.** День считается выгруженным, только если
   выгрузка прошла после его окончания. Идемпотентность прошлого сохраняется,
   сегодняшний день остаётся перезапрашиваемым — на этом и стоит обновление.
3. **Заявка из интерфейса.** Шлюз публикует `CrawlRequested` с идентификатором
   задания; кнопка на экране мониторинга показывает ход по `GET /jobs/{id}`.

Регионы: `EIS_REGIONS` начинает понимать `all` и разворачивается в справочник
на 85 субъектов из `libs/shared/regions.py`. Фильтрация по регионам в каталоге
и в форме исследования уже работает и не трогается.

## Этап 1. Один сценарий выгрузки

**Инвариант под угрозой:** правило отбора живёт в одном месте (CLAUDE.md §4).
Здесь тот же принцип, но про сбор: один сценарий на одну ответственность.

### Изменения

- Удалить `CrawlAllUseCase` ([crawl_tenders.py:94](../../services/crawler/application/use_cases/crawl_tenders.py#L94))
  и фабрику `CrawlerContainer.crawl_all` ([bootstrap.py:49](../../services/crawler/bootstrap.py#L49)).
- `_crawl_days` ([cli.py:148](../../services/crawler/presentation/cli.py#L148))
  переписать на `container.crawl_period().execute(regions, date_from, date_to)`.
  Транзакция из `presentation` уходит — её открывает `SessionScopedCrawlRunner`
  на каждую выгрузку, как и задумано в его докстринге.
- `--days-back N` превращается в `date_from = вчера - (N-1)`, `date_to = вчера`.

**Что это даёт даром:** параллельность по уровню нагрузки, посуточные
транзакции, пропуск уже выгруженного. Дневной проход становится идемпотентным —
перезапуск контейнера перестаёт перекачивать вчерашний день.

**Чего делать нельзя:** поднимать `crawl_workers` выше шести.
`MAX_CRAWL_WORKERS = 6` — замеренный потолок ЕИС
([load_policy.py:63](../../libs/shared/load_policy.py#L63)), бан прилетает на
весь прогон, а не на одну выгрузку.

### Тесты

- `_crawl_days` зовёт период с верными границами при `--days-back 1` и `3`.
- Повторный запуск в тот же день не порождает новых выгрузок (пропуск работает).
- Существующие 15 тестов `test_crawl_period.py` обязаны остаться зелёными без
  правок — это и есть проверка, что поведение не поехало.

**Регрессия:** полный `pytest`, `lint-imports` (4 контракта), `ruff`.
Сквозная: `docker compose up -d crawler` на `EIS_REGIONS=77`, в
`crawler_runs` одна успешная строка за вчера, повторный старт — ноль новых.

## Этап 2. День завершён — только когда он кончился

**Инвариант под угрозой:** знаменатель обязателен (CLAUDE.md §6). Дыра в
покрытии, помеченная как успех, — ровно тот случай, когда «находок нет»
неотличимо от «не смотрели».

### Изменения

Правило принадлежит домену выгрузки, а не SQL. Ввести в
`services/crawler/domain/` предикат:

```python
def is_final(target_date: date, ran_at: date) -> bool:
    """Суточный архив ЕИС дописывается до конца суток."""
    return ran_at > target_date
```

`SqlCrawlRunLog.completed` ([run_log.py:42](../../services/crawler/infrastructure/db/run_log.py#L42))
добавляет условие `CrawlerRun.started_at > CrawlerRun.target_date + 1 день`.
Условие выражается в SQL, но **формулируется в домене** — репозиторий его
применяет, а не изобретает.

### Следствия

- Сегодняшний день всегда перезапрашивается → обновление работает без флага
  `force`. Флага и не заводим: он был бы вторым способом сказать то же самое.
- Прошлые дни по-прежнему пропускаются → «догоняет, а не переделывает»
  сохраняется.
- Дневное расписание не меняется: оно берёт вчера, и первый же проход после
  полуночи финален.

### Тесты

- День, выгруженный в тот же день, в `completed()` не попадает.
- День, выгруженный на следующий, попадает.
- Заявка на период, включающий сегодня, порождает выгрузку сегодня и пропускает
  прошлые дни.
- Регрессия существующего: `test_crawl_period.py::...skips_completed` должен
  быть подправлен по датам, но не по смыслу.

**Регрессия:** полный `pytest`. Сквозная: дважды заказать период
`[вчера, сегодня]` — второй раз выгружает только сегодня.

## Этап 3. Заявка из интерфейса

### 3.1 Кто публикует

Шлюз. `CrawlRequested` — команда, адресованная краулеру; краулер HTTP не
слушает и слушать не должен (он воркер без портов). Проксировать через
llm-service нельзя: он не владеет выгрузкой, и такой маршрут был бы враньём про
владельца.

**Это не нарушение инварианта «сервисы связаны только событиями и HTTP»** —
наоборот, ровно его исполнение. Шлюз перестаёт быть исключительно читателем, и
это осознанное изменение: принимать команды и передавать их владельцу — работа
шлюза.

Новое в `services/api`:

```
application/ports/crawl.py      CrawlPublisherPort (protocol, DIP)
infrastructure/messaging/       RabbitCrawlPublisher — единственный, кто знает AMQP
presentation/routers/crawl.py   POST /crawl  → 202 {job_id}
```

`Ports` ([registry.py:39](../../services/api/application/ports/registry.py#L39))
получает `crawl: CrawlPublisherPort`. Соединение поднимается в lifespan рядом с
остальным.

**Проверка контракта:** `lint-imports` обязан остаться зелёным — `presentation`
шлюза не знает реализаций, только порт.

### 3.2 Ход выполнения

`CrawlRequested` получает поле `job_id: uuid.UUID | None = None` — добавление
поля контракт разрешает. Краулер, получив заявку с `job_id`, ведёт строку в
`jobs` тем же `SqlJobTracker`, что и research: `start(kind="crawl", total=числу
выгрузок)`, `progress` по завершении каждой, `finish` с итогом
`PeriodOutcome`. Это третий потребитель таблицы заданий и второй, показывающий
проценты, — механизм уже обкатан.

Заводить `jobs` в краулере — своя копия трекера, как в research и llm-service:
сервисы не импортируют друг друга, общая у них таблица, а не код.

### 3.3 Что именно запрашивает кнопка

Окно обновления — **сегодня и вчера**: ЕИС публикует с задержкой, и вчерашний
архив к утру ещё дописывается. Прошлые дни отсекутся правилом этапа 2 сами.

```
POST /crawl  {"since": "2026-08-13", "until": "2026-08-14", "regions": []}
     → 202 {"job_id": "..."}
```

Пустые регионы — все настроенные. Валидация: `until >= since`, коды регионов
против `RUSSIAN_REGIONS`, глубина периода не больше 90 дней (заявка на год из
интерфейса — способ случайно устроить себе бан).

### 3.4 Интерфейс

Кнопка «Обновить» на `/monitoring/crawler` — рядом с журналом выгрузок, там же,
где видно результат. Слайс `features/request-crawl/`, образец —
`features/run-research/`: мутация → `setJobId` → `useJob` → `PendingBlock` →
инвалидация `qk.monitoring.*`. Подпись под кнопкой говорит правду о механике:
ЕИС отдаёт суточные архивы, поэтому обновление перекачивает последние два дня,
а новыми окажутся только те извещения, которых ещё не было.

Строки в `ru.monitoring.*`. Литералов в JSX нет — правило §10 брифа.

### Тесты

- Схема запроса: принимает регионы и период, отвергает перевёрнутый период,
  неизвестный регион, период глубже 90 дней.
- Опубликованное событие несёт `job_id`, регионы и границы.
- Краулер ведёт задание: `start` с числом выгрузок, `finish` с итогом; заявка
  без `job_id` работает как раньше (обратная совместимость контракта).
- `lint-imports`: presentation шлюза не видит `RabbitCrawlPublisher`.
- Vitest: кнопка блокируется на время прогона, ошибка показывается на месте.

**Регрессия:** полный `pytest`, `lint-imports`, `pnpm lint && typecheck && test`.
Сквозная: нажать «Обновить» → задание живёт, проценты растут, в `crawler_runs`
строки за сегодня, повторное нажатие через минуту — выгрузка идёт снова
(сегодня не финален), новых закупок ноль.

## Этап 4. Вся Россия

Делается последним намеренно: он умножает нагрузку, и все предыдущие этапы —
условия, при которых это безопасно.

### 4.1 Конфигурация

`EisSettings.region_list` ([config.py:74](../../libs/shared/config.py#L74))
понимает сентинел:

```
EIS_REGIONS=all      → tuple(RUSSIAN_REGIONS)   # 85 субъектов
EIS_REGIONS=77,78    → как сейчас
```

Справочник берётся из `libs/shared/regions.py` — того самого, что уже
подписывает разрезы рынка и питает пикер регионов. Второго списка не заводим.

### 4.2 Чего это стоит

Одна выгрузка = SOAP-запрос + скачивание суточного архива + разбор в память.
85 регионов × 1 тип × 1 день при шести рабочих — **числа неизвестны, и это
главный риск этапа.**

Поэтому первым шагом — замер, а не переключение:

```bash
EIS_REGIONS=all .venv/bin/python -m services.crawler --once --days-back 1
```

Замерить и записать в [baseline.md](baseline.md): время полного обхода, пик
памяти (шесть архивов в памяти одновременно), число извещений за сутки по
России, долю регионов, ответивших пустотой или отказом.

**Пороги, при которых этап останавливается и пересматривается:**

- обход не укладывается в интервал расписания (60 мин) → интервал или
  параллельность придётся менять, а параллельность упёрта в потолок ЕИС;
- пик памяти краулера подходит к лимиту контейнера → архивы надо потоково
  разбирать, а не держать целиком, и это отдельная работа;
- ЕИС начинает отказывать на части регионов → нужен разъезд по времени, а не
  по параллельности.

### 4.3 Что поедет следом

- **`crawler_runs` растёт с 1 до 85 строк в день.** Экран выгрузок
  (`/monitoring/crawler`) читает их построчно — понадобится группировка по дню
  с раскрытием, иначе журнал станет нечитаемым за неделю.
- **Фасет регионов обрезан двадцатью корзинами**
  (`FACET_LIMIT = 20`, [facets_repository.py:34](../../services/api/infrastructure/db/facets_repository.py#L34)).
  Пикер показывает все 85 из статического справочника, но счётчики придут
  только для двадцати. Либо поднять предел для регионов (их конечное число),
  либо честно не показывать счётчик там, где его нет. Первое проще и честнее.
- **Объём документов.** Вложения качает `docs-worker` по событию; рост числа
  извещений в десятки раз означает такой же рост очереди. Уровень нагрузки его
  придушит (`docs_prefetch`), но выгрузка перестанет быть «за ночь». Это
  ожидаемо и управляемо, но должно быть сказано вслух до, а не после.

### 4.4 Что не меняется

Фильтрация по регионам работает уже сейчас и на всех трёх экранах: фасет
каталога, чип условия, форма исследования. Ни строки менять не нужно —
изменится только наполнение.

### Тесты

- `region_list` разворачивает `all` в 85 кодов, обычный список — как раньше,
  пустая строка — пусто.
- Заявка на 85 регионов порождает 85 выгрузок и не превышает потолок рабочих.

**Регрессия:** полный `pytest`, `lint-imports`, фронт целиком. Сквозная: сутки

## Порядок и сеть безопасности

| Этап | Меняет | Откат |
|---|---|---|
| 0 | только тесты | тривиален |
| 1 | горячий путь сбора | вернуть `CrawlAllUseCase` из истории |
| 2 | правило пропуска дней | снять условие в `completed()` |
| 3 | новый маршрут и слайс | маршрут не звать |
| 4 | одну переменную окружения | `EIS_REGIONS=77` |

Этапы 1–3 не зависят друг от друга по коду, но зависят по смыслу: кнопка без
правила завершённости обновляет пустоту, а вся Россия без сведения сценариев
упирается в одну транзакцию на 85 регионов. Порядок соблюдать.

**После каждого этапа:**

```bash
DB_HOST=localhost .venv/bin/python -m pytest tests/ -q
.venv/bin/python -m ruff check .
.venv/bin/lint-imports
cd web && pnpm lint && pnpm lint:boundaries && pnpm typecheck && pnpm test
```

Золотой набор — на каждой границе этапов: 56 подтверждённых не теряются,
20 отклонённых не проходят. План не трогает `services/research/domain/`, поэтому
любое движение этих чисел означает, что сломалось что-то неожиданное.

**Отдельно про пересборку контейнеров.** `docker compose up -d --build <сервис>`
собирает образ, но **не пересоздаёт контейнер** — на этом уже дважды сгорели
проверки: старый код в `research` дал неверный знаменатель, старый фронт не
показал новых кнопок. Сквозная проверка любого этапа начинается с
`docker compose up -d --force-recreate <сервис>`.

## Чего в плане намеренно нет

- **Запроса «что нового с момента X».** У ЕИС суточная гранулярность; такой
  запрос пришлось бы имитировать перекачкой архива, то есть тем же, что делает
  обновление. Отдельное имя для той же механики создало бы ложное ожидание.
- **Флага `force` у заявки.** Правило завершённости дня решает ту же задачу и
  не даёт способа случайно перекачать полгода.
- **Расписания «каждые N минут по всей России».** Сначала числа из 4.2, потом
  разговор об интервале.
- **Автозапуска исследования после выгрузки.** Заманчиво, но связывает сбор с
  отбором; исследование запускается человеком и остаётся таким.
