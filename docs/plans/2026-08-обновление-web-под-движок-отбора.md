# Обновление web под новый движок отбора

Продолжение [`FRONTEND_BRIEF.md`](../../FRONTEND_BRIEF.md) и
[`FIX_BRIEF.md`](../../FIX_BRIEF.md). Бэкенд заменил движок фильтров и завёл
сервис исследований — интерфейс об этом ещё не знает.

**Рабочие правила прежние** (взяты из `FIX_BRIEF.md` §0 и подтверждаются здесь):

- Минимальные диффы. Не переписывать работающие компоненты, не форматировать
  нетронутые файлы, не «улучшать заодно».
- Каждая правка — **механизм**, а не заплатка на симптом.
- Границы слоёв целы: сырая палитра и расчёты вёрстки в `shared/`, доменный
  словарь в `entities/`, композиция в `widgets/`. `pnpm lint:boundaries` чист.
- Каждый раздел приезжает со сторожевым тестом. Правка без сторожа не сделана.
- DTO руками не пишутся: `pnpm gen:api`. Нет эндпоинта — раздел
  останавливается и пишется в `web/docs/API-GAPS.md`.
- Итог записать в `web/docs/CHANGELOG.md`; `web/docs/DESIGN.md` править там,
  где меняются сами правила показа (§3, §4).

## 0. Главное: цепочка сейчас разорвана

Прежде чем планировать экраны — про дефект, который делает половину этой
работы бессмысленной, пока он не исправлен.

`POST /filters/compile` по-прежнему отдаёт **старый** `FilterSpec`, а движок
отбора принимает **новый** критерий. Проверено:

```
spec из /filters/compile: customer_inns, date_range, keywords, llm_criteria,
                          okpd2_prefixes, only_active …
движок отбора: CriteriaError — «критерий без терминов ничего не найдёт»
```

Практически это значит: пользователь создаёт фильтр в конструкторе, нажимает
«Запустить», получает `202 Accepted` и `job_id` — а прогон падает в лог и не
делает ничего. Ни ошибки на экране, ни результата.

**Это чинится на бэкенде и первым делом.** Никакая работа по интерфейсу не
имеет смысла, пока конструктор производит спецификацию, которую движок не ест.

| Что | Где |
|---|---|
| `CompileFilterUseCase` должен выдавать новый критерий | `services/llm_service/application/use_cases/compile_filter.py` |
| Промпт компиляции — про термины и правила по контексту, а не про ключевые слова | `services/llm_service/application/prompts.py` |
| Схема структурного вывода — `terms[]`, `context_rules[]`, `card_pattern` | там же |
| Запуск с непригодным критерием обязан **валить задание**, а не молчать | `services/research/presentation/worker.py` |

Последняя строка важна отдельно: сейчас непригодный критерий пишет `log.error`
и возвращает управление, задание остаётся висеть в `running` навсегда. Должно
быть `jobs.fail(job_id, причина)` — иначе интерфейс честного состояния не
покажет при всём желании.

Пока это не сделано, разделы §2–§4 писать не по чему.

## 1. Что изменилось в API

Сводка для тех, кто будет читать диффы схемы.

| Было | Стало | Кого задевает |
|---|---|---|
| `filter.evaluate.requested` | `research.requested` | внутреннее, UI не видит |

| Воронка: `total → after_structural → after_semantic → after_judge` | Воронка ветвится: правила / кэш / модель | **экран проверки фильтра** |

| — | прогоны, находки, рыночная сводка | **новый раздел** |

## 2. Конструктор фильтра — три панели описывают не тот движок

`FRONTEND_BRIEF.md` §5.6 задаёт три панели «в том порядке, в каком реально
работает конвейер». Конвейер стал другим, значит и панели другие. Это не
косметика: панель «Семантический запрос» описывает этап, которого больше нет.

**Было** (пайплайн: SQL → вектор → судья):

```
1. Структурные условия     ← поле/оператор/значение
2. Семантический запрос    ← textarea + «похоже на»
3. Критерий для ИИ-судьи   ← vellum textarea
```

**Стало** (пайплайн: предфильтр → термины → контекст → судья по спорным):

```
1. Где искать              ← предфильтр по карточке + префиксы ОКПД2
                              «Сужает круг до закупок, где упоминание вообще
                               возможно. Намеренно широкий.»
2. Что искать              ← термины: [шаблон][роль: основной/вспомогательный]
                              живой предпросмотр совпадений на трёх примерах
3. Как отличить своё       ← правила по контексту:
                              [шаблон][за/против][окно ±N символов]
                              «Отсекает мусор до обращения к модели.»
```

Панель 3 — новая по смыслу и **главная по ценности**: именно она в замере
отсекла все 20 ложных срабатываний без единого токена. Её надо объяснить
пользователю, а не спрятать как «дополнительные настройки».

**Роль термина показывать явно.** Основной/вспомогательный — не деталь: закупка,
где сработали только вспомогательные, отвергается целиком. В замере это шесть
медицинских закупок из двадцати. Подпись у переключателя: «Вспомогательный сам
по себе ничего не значит — усиливает основной».

**Окно у правила по контексту** — число со смыслом, а не ползунок «чувствительность»:
±60 символов ≈ три-четыре слова. Подпись: «Смотреть вокруг совпадения». Правила
«против» с широким окном ловят посторонний шум — это стоит сказать в подсказке.

**Живой предпросмотр вместо «похоже на».** Панель 2 показывает, что шаблон
находит в трёх реальных цитатах из корпуса, с подсветкой совпадения. Это дешёвая
замена исчезнувшему семантическому предпросмотру и объясняет шаблон лучше любого
описания.

**Сторож:** снимок формы конструктора для критерия ХПК/БПК — три панели, роли
терминов, окна правил; тест падает, если панель потеряла поле.

## 3. Воронка проверки перестала быть каскадом

`FRONTEND_BRIEF.md` §5.6 называет воронку «самым полезным на странице», и это
по-прежнему так. Но рисовать её прежней лестницей больше нельзя: этапы не
вложены друг в друга.

**Было** — каждый следующий этап подмножество предыдущего:

```
Все за 30 дней        4 812  ████████████████████
После структурных       318  ██
После семантики          96  ▊
После судьи              41  ▎
```

**Стало** — после находок поток **разветвляется**, и три ветви равноправны:

```
Рассмотрено           4 812  ████████████████████
  ├ отсеяно правилами    20  ▏      ← бесплатно
  ├ принято правилами    48  ▎      ← бесплатно
  └ спорные               8  ▏      → к модели
        ├ из кэша         3
        ├ спрошено        5
        └ не дошло        0         ← модель легла
```

Рисовать это лестницей — врать: «принято правилами» не является подмножеством
«отсеяно правилами». Форма — **ветвление**, и `DESIGN.md` §4 (шкала сроков) даёт
готовый язык для такой формы: та же логика отступления подписей, тот же ритм.

Два числа, которых раньше не было и которые обязаны быть на экране:

- **«не дошло»** — модель легла на середине. Без него «спорных 8, решено 5»
  выглядит как потеря, хотя это остановка.
- **«не прочитано»** — документы без извлечённого текста
  (`ScanStats.documents_pending`). Это знаменатель: «находок нет» имеет смысл
  только рядом с «прочитано столько-то». Ретроспектива описывает, как его
  отсутствие привело к ложному выводу — не повторять на экране.

**Сторож:** тест арифметики — сумма ветвей сходится с «рассмотрено»; тест на
подпись «не дошло», появляющуюся только при `interrupted`.

## 4. Цитаты: теперь есть что подсвечивать

Форма `evidence` сменилась: `chunk_id` → `hit_number`, и вместе с находкой
приезжают `match_start`/`match_end`.

Это закрывает урок ретроспективы §2.7 прямо в интерфейсе: раньше цитата
показывалась как есть, и при обрезке было видно только левый контекст —
несколько неверных выводов родились именно так. Теперь совпадение можно
выделить:

```
… нефтепродукты, железо общее, аммоний-ион, [БПК5], сульфиды …
```

- `entities/verdict/ui/verdict-note.tsx` — ключ списка `${hit_number}-${index}`
  вместо `${document_id}-${chunk_id}-${index}`.
- Подсветка — примитив в `shared/ui`, а не разметка внутри карточки: цитаты
  показываются в трёх местах (вердикт, инспектор, отчёт), и вставлять `<mark>`
  руками в каждом — та самая заплатка вместо механизма.
- Обрезка длинной цитаты (`§8.3`) обязана **сохранять совпадение в кадре**:
  резать по краям от `match_start`/`match_end`, а не от начала строки. Это и
  есть настоящая правка урока §2.7.

**Ссылка на источник.** `chunk_id` больше нет, значит прежний
`citationHref` в документ по чанку не построить. Пока в API нет перехода
«находка → место в документе», ссылка деградирует до документа целиком
(`file_name`, `page`), а несуществующий якорь **не выдумывается**. Записать в
`API-GAPS.md`.

**Сторож:** тест обрезки — совпадение остаётся видимым при любой длине цитаты.

## 5. Просмотрщик документа: ссылка ведёт наружу

`expires_in: 0` и внешний адрес ЕИС. Копий файлов система больше не хранит.

- Подпись `[Скачать оригинал]` — «Открыть в ЕИС», с внешней иконкой.
- Убрать всё, что обещает временную ссылку: `expires_in: 0` означает не
  «истекла», а «сроком распоряжаемся не мы».
- Честное состояние, когда `source_url` пуст (файл из архива — у него своего
  адреса в ЕИС нет): «Оригинал доступен только внутри архива-вложения».

**Сторож:** тест на `expires_in: 0` — компонент не показывает таймер и не зовёт
ссылку временной.

## 6. Мониторинг документов: появились «отложено» и причина отказа

Воронка `/monitoring/documents` знает `pending/done/skipped/failed`. Добавились:

- **`deferred`** — отложено настройками, вернётся при более щедром прогоне.
  Показывать **отдельно от `skipped`**: это принципиально разные состояния, и
  смешать их — потерять то самое различие, ради которого на бэкенде заведён
  отдельный статус.
- **`skip_reason`** — разбивка отказов: том многотомного архива, не влез в
  бюджет закупки, слишком крупный, подпись. Разбивка объясняет цифру «разобрано
  115 тыс. из 198 тыс.», которая без неё выглядит как поломка.

Подписи причин — доменный словарь, значит `entities/`, а не строки в виджете.

**Сторож:** снимок воронки со всеми статусами, включая нулевые ветви.

## 7. Уровень нагрузки — на экран настроек

`GET/PATCH /system/load-level`. По `FRONTEND_BRIEF.md` §5.10 настройки
«read-mostly, потому что конфигурация живёт в `.env`» — **это исключение и
единственный на экране настоящий переключатель**. Так его и подать.

Три состояния, подписи по смыслу, а не по номеру:

```
( ) Фоновый    — не мешать другой работе на этой машине
(•) Средний    — по умолчанию
( ) Полный     — машина отдана под анализ
```

Рядом — что из этого следует, числами из ответа: процессов разбора, prefetch,
одновременных обращений к модели, потолок к ЕИС. И честная оговорка: **числа
посчитаны для машины шлюза**, у воркера с другим лимитом памяти пул может
отличаться.

Отдельная строка, которая избавит от вопроса «почему не применилось»:
переключение асинхронное, воркеры сверяются с настройкой раз в ~15 секунд.
Показать это ожиданием, а не мгновенной «галочкой».

**Сторож:** тест — PATCH с недопустимым уровнем даёт 422 и сообщение, а не
молчаливое приведение к среднему.

## 8. Определение деградации сломано

`FRONTEND_BRIEF.md` §9.6 определяет деградацию по `llm_criteria` + `keywords`.
Обоих полей больше нет — функция `isDegraded` сейчас всегда возвращает `false`,
то есть баннер «ИИ недоступна» не покажется никогда.

Новый признак честнее прежнего эвристического: движок сам сообщает, что модель
легла, — `interrupted` в результате прогона и ветвь «не дошло» в воронке. Плюс
`/judge` у llm-service отвечает `503`, когда модель недоступна.

```ts
// features/compile-filter/lib/detect-degraded.ts → переписать
export function isDegraded(result: ResearchResult): boolean {
  return result.interrupted || result.funnel.not_reached > 0;
}
```

Баннер и его поведение (липкий на сессию, скрываемый, возвращается на следующем
деградированном ответе) — как в §9.6, менять не надо.

**Сторож:** тест на `interrupted: true` → баннер; на обычный ответ → нет.

## 9. Новый раздел: исследования

Самое крупное добавление. Движок пишет прогоны, находки и рыночную сводку —
показывать это негде.

**Чего в API нет.** Шлюз наружу их пока не отдаёт: таблицы `research_runs`,
`research_hits`, `research_verdicts` заполняются, эндпоинтов нет. По правилу
брифа (§9.1) раздел не начинается, пока не появятся:

```
GET  /research/runs                  список прогонов с воронкой
GET  /research/runs/{id}             прогон: критерий, воронка, длительность
GET  /research/runs/{id}/tenders     закупки прогона: вердикт, кем решено, цитаты
GET  /research/runs/{id}/market      разрезы: регион, заказчик, ОКПД2, чек
POST /research/runs                  запуск: критерий, регионы, период
```

Это **работа по бэкенду**, и её объём сопоставим с самим разделом. Записать в
`API-GAPS.md` с точными формами — не выдумывать клиентский обход.

Когда эндпоинты появятся, экраны выстраиваются так:

- **`/research`** — список прогонов: критерий, период, регионы, воронка одной
  строкой, длительность. Карточка прогона — тот же язык, что у карточки фильтра.
- **`/research/[id]`** — воронка из §3 крупно, под ней две вкладки:
  «Закупки» (вердикт, кем решено, цитата с подсветкой) и «Рынок».
- **Рынок** — разрезы по региону, заказчику, ОКПД2. Обязательно **медиана рядом
  со средним**: распределение с тяжёлым правым хвостом, и одно среднее описывает
  рынок, которого нет. Показать это явно, а не оставить читателю.
- **Заказчики группируются по ИНН.** В замере под одним названием «Центр гигиены
  и эпидемиологии» оказались четыре разных юрлица. Подпись — название, ключ —
  ИНН; при совпадении названий показывать ИНН рядом, иначе на экране появятся
  два одинаковых заказчика без объяснения.

## 10. Порядок работ

Разделы упорядочены так, что каждый следующий опирается на сделанное.

| # | Что | Почему здесь |
|---|---|---|
| 0 | **Бэкенд: компиляция в новый критерий + падение задания** | без этого конструктор производит нерабочее |
| 1 | `pnpm gen:api`, починить типы, `pnpm typecheck` зелёный | остальное правится по типам, а не наугад |
| 2 | Цитаты и подсветка (§4) | примитив нужен и конструктору, и исследованиям |
| 3 | Конструктор фильтра (§2) | главный сломанный экран |
| 4 | Воронка (§3) | вместе с конструктором это один сценарий |
| 5 | Деградация (§8), просмотрщик (§5), воронка документов (§6) | мелкие, независимые |
| 6 | Уровень нагрузки (§7) | самостоятельный экран |
| 7 | **Бэкенд: эндпоинты исследований** | предусловие раздела |
| 8 | Раздел исследований (§9) | самое крупное, идёт последним |

Пункты 0 и 7 — бэкенд. Пункты 1–6 можно делать, не дожидаясь 7.
